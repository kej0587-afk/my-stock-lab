## 결론

이전 지적이 전부 현재도 남아 있는 것은 아니다. SQZ 인자와 짧은 봉 처리, 개별주 패닉 투입 차단, 52주 돌파의 당일 고가 제외 등은 이미 수정된 코드와 회귀 테스트가 있었다. 반면, 자료가 없을 때 정상 점수를 부여하는 경로와 실전 판정/과거 기술신호 검증의 차이는 여전히 중요한 문제다.

이번에는 후보 제한 우회, 하드차단의 설명문 의존, 실시간 지표 재계산 실패, 저장 결과의 사용자 혼용, RS 가격 기준 혼용 등을 수정했다. 매매 임계값을 완화하거나 신규 추천 종목을 늘리지는 않았다. 전체 코드가 무결하거나 투자 성과가 검증됐다는 결론은 아니다.

### P1. 재무 미조회가 3점으로 표시될 수 있음

근거: [기본 재무점수](<C:/Users/82amf/OneDrive/바탕 화면/주식/my-stock-lab/app.py:3569>), [미계산 조회](<C:/Users/82amf/OneDrive/바탕 화면/주식/my-stock-lab/app.py:5992>), [간이 점수](<C:/Users/82amf/OneDrive/바탕 화면/주식/my-stock-lab/stock_lab_core/financial_score.py:40>).

`AUTO_FIN_FAIL_SCORE`와 `UNCALCULATED_FIN_DEFAULT_SCORE`가 3이다. 일부 호출부가 조회 상태를 버리고 정수 점수만 사용하므로, 미확인이 실제 재무 양호와 같은 등급 근거가 될 수 있다. 이것이 가장 먼저 정리할 데이터 의미 문제다.

이번에는 3을 0으로 바꾸지 않았다. 0점은 다른 곳에서 재무 위험/차단으로 해석되므로, 조회 실패를 매도 사유로 바꾸는 부작용이 있다. `score: None`, `status`, `source`, `asof`를 갖는 결과형을 도입하고 화면, 저장, 후보 품질, 보유 판정까지 함께 전달해야 한다. 실제 결측과 실적 악화는 별개다.

## 구조 수치와 후속 순서

현재 `app.py`는 37,226줄, 함수 865개(중첩 포함), 300줄 초과 함수 14개, 150줄 초과 함수 37개다. `calc_scores_and_decision`은 1,342줄이고 포트폴리오 렌더링은 839줄이다. 이번은 위험 경로 수정과 저장 책임 분리이지 대형 UI 파일 분해 완료가 아니다.

최상위 try는 4개다. 과거 리뷰의 21개와 현재 수치를 혼용하면 안 된다. 넓은 예외 처리 173개 중 본문이 pass/continue/return만 있는 후보는 88개다. 이는 정적 검색 후보 수이지 확정 버그 수가 아니다. `iterrows` 81회, `apply(axis=1)` 89회도 일괄 제거 목표로 삼지 않는다.

1. 재무/매크로의 값과 조회 상태를 분리한다. 미확인, 오래됨, 실제 악화를 서로 다른 상태로 전달한다.
2. 실시간 호가와 확정 봉을 분리한다. 시각/세션/가격조정 기준/실거래량을 보존한다.
3. 후보 품질, 공통 실행 게이트, 최종 표시의 입출력을 고정한다. 코드/상태 기반으로 분류하고 설명문 정규식 의존을 점진적으로 줄인다.
4. 과거 조건 재생과 실전 로그 평가를 분리한다. 다음 봉 체결과 신호 종가 관찰, 비용, 중복 표본 옵션을 명시한다.
5. 가격/뉴스/재무 API를 성공 캐시 및 제한된 실패 재시도로 묶고, 중복 조회를 계측한다.
6. 이 계약에 맞춰 입력 dataclass와 계산 단계를 분리한 뒤 화면별 렌더링을 이동한다. 함수의 위치만 옮겨 동일한 전역 의존을 복제하지 않는다.
7. 별도 단계로 owner 필수 DB 저장소와 인증/RLS 마이그레이션을 검증한다.

각 단계의 완료 기준은 정상 사례뿐 아니라 결측, 공급자 실패, 다른 사용자, 오래된 결과, 패턴 우회, 고정 golden 판정이 함께 통과하는 것이다.

## 검증 결과와 한계

- 수정 전 후보/게이트 충돌 4건과 손상 스냅샷 처리 4건을 테스트 실패로 재현한 뒤 수정했다.
- 전체 회귀 테스트: **654개 통과**, 27.59초. 기존 pykrx deprecation 경고 1개가 남았다.
- 세 진입점/core/tests 문법 검사 및 내부 import 계약 검사 통과. 기존 판정문구 golden 테스트 통과.
- 스냅샷 사용자 분리, 서명 불일치, 앞자리 0, 실패한 파일 교체, 4개 스레드 12회 저장, 손상된 표 구조를 검증했다.
- 피벗: 1,500봉 합성 데이터, 각 7회 중앙값. 내부 피벗 93.54ms에서 1.63ms, 외부 피벗 92.87ms에서 0.76ms. 두 경우 기존 결과와 일치했다. 별도 동가/NaN/짧은 이력/확정 폭 테스트도 통과했다.
- 이 수치는 피벗 함수의 로컬 측정치다. 앱 전체 초기 로딩이나 외부 API 지연이 57배 이상 개선됐다는 의미는 아니다.
- 실제 브라우저 전 화면, 인증된 Supabase 저장, 외부 API 장애/실시간 시세 정확도, 투자 성과 백테스트를 이번에 새로 실행하지 않았다.

## 반영 시 주의점

로컬 코드만 수정했다. Git push나 Streamlit Cloud 배포는 하지 않았다. 배포할 때 새 `today_snapshot.py`를 포함한 core 파일, 진입점, requirements를 함께 반영해야 한다.

판정 버전은 `20261012_data_gate_snapshot_v6`이다. 이전의 공용 디스크 스냅샷은 자동 복원하지 않는다. 배포 후 오늘점검을 한 번 다시 계산해야 한다. 같은 사용자 세션에서는 마지막 결과를 유지하며 입력 변경 시 오래된 결과임을 알린다. 공개 체험모드는 개인 디스크 스냅샷을 읽거나 쓰지 않는다.

사용자 해시는 파일 분리 수단이며 암호화가 아니다. 로컬 JSON에는 결과 데이터가 남는다. 이 스냅샷은 서버 파일이며 영구 DB 백업을 대체하지 않는다. 실전 신호 journal과도 별개다.
