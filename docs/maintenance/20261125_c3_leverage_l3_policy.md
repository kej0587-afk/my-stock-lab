# C-3 레버리지 L3: L2 자격 → 회복 확인 → 사전 예산 1/3 회차 (2026-11-25)

사용자 결정(2026-11-25, C-3 비교 후): 레버리지 DCA는 "많이 떨어졌으니 매수"가 아니라
"충분히 하락해 DCA 후보가 됨(L2) → 회복 확인(L3) → 사전 예산 중 한 회차만 실행" 구조입니다.
약세장 초입의 가짜 회복은 회복조건으로 다 막을 수 없으므로, 1/3 회차, 최대 3회, 총예산 한도, −50% 패닉 latch,
시장방어 우선으로 관리합니다.

비교 보고서: `/mnt/project-files/reports/20261125_c3_leverage_l3_comparison.md`
고정 입력 재생: `/mnt/project-files/reports/20261125_c3_l3_policy_replay.md`

## 규칙표

| 항목 | 규칙 |
|---|---|
| L3 회복조건 | 시장방어 아님, 기초지수 MA50 위, 레버리지 ETF MA50 위, 회복체크 4/6 이상, 기존 차단 없음 (D안 + 4/6). 구조회복은 필수 아님 |
| 기존 차단 | 패닉(−50%), 일일급락(−8%), 과열(%B·RSI·MFI·당일 +8%), 시장방어, 매크로, 데이터, 비중(목표 0·충족) 그대로 |
| L2 자격 | 이번 하락 사이클에서 평단 대비 −12% / −25% / −35% 중 하나를 한 번이라도 충족하면 기록. 이후 손실이 −12%보다 작아져도 L3 평가 가능 |
| 사이클 시작 | 52주 고점 대비 −10% 이하인 완료봉 (열린 사이클이 없을 때) |
| 사이클 종료 | 포지션 종료(수량 0), 또는 패닉 latch가 풀린 상태에서 52주 신고가 종가(지난 1년 모든 종가 위) |
| 패닉 latch | 52주 고점 대비 −50% 이하 완료봉에서 발동. 52주 고점이 내려와 낙폭이 줄어도 풀리지 않음. 해제는 같은 봉에서 기초 상승장(종가 > 200일선, 200일선 20일 상승) + 기초·레버리지 MA50 위 + 회복 4/6 |
| 목표비중 충족·0 | L3만 막고 사이클 상태(자격·latch·회차)는 유지 |
| 회차 | 사전 레버리지 DCA 예산의 1/3, 최대 3회. 다음 회차는 마지막 실제 실행 기록일로부터 해당 거래소 완료 거래일 20일 이상 지나고, 그 봉에서 L3 조건을 처음부터 다시 모두 만족해야 함(2단계 결정, 선택지 A). 20일이 지나도 자동 실행하지 않음 |
| 회차·쿨다운 유지 | 조건이 중간에 사라졌다 다시 나타나도 쓴 회차와 20거래일 쿨다운 유지. 사이클이 정상 종료(위 사이클 종료)될 때만 초기화 |
| 회차 금액 | min(예산/3, 예산 − 누적 투입, 목표비중 부족분 − 이번 달 월적립 배분) |
| 예산 미설정 | L3 후보로만 표시, 실행가능 아님 |
| 회차 소진 | 사용자가 정밀관측소에서 "L3 n회차 실행 기록"을 눌러 실제 실행을 기록할 때만. 신호 발생, rerun, 새로고침, Today 재계산, 화면 조회로는 줄지 않음 |
| 실행가능 조건 | L3 조건 + 예산 설정 + 남은 회차 + 20거래일 경과 + 이번 달 월적립 배분 확인 + (L3 금액 + 월적립 배분) ≤ 목표비중 부족분. 예: 계획 100만, 부족분 70만, 월적립 30만 → 최대 40만 |

## 월적립과 중복 집행 방지

- 월적립 계산기(`monthly_rebalance_view`)는 원 엔진 판정과 자체 레버리지 하락 배율(평단 −5/−10/−15%에서
  ×0.75~×2.0)로 월 적립금을 나눕니다. 이것은 정기 적립 풀입니다.
- L3는 별도의 위기/DCA 예산 풀입니다. 같은 목표비중 부족분을 두 번 채우지 않도록, L3 회차 금액은
  "목표비중 부족분 − 이번 달 월적립 배분"을 넘지 못합니다(`tranche_amount`).
- 이번 달 월적립 배분을 알 수 없으면 실행가능으로 만들지 않습니다(사유 "이번 달 월적립 배분 미확인").
- 월적립 배율 표와 parity의 가상 t_mult는 바꾸지 않았습니다.

## 앱 적용 범위

1단계(PR #46): 상태기계와 L3 후보 표시.

- `stock_lab_core/leverage_l3_policy.py`: 사이클 상태기계(`LeverageDcaCycle`, `step`, `replay`),
  완료봉 이력 → 봉 목록(`build_history_bars`), 현재 봉 판독(`read_current`), 화면 문구.
- `app.build_leveraged_l3_read`: 보유 중인 레버리지 ETF(TQQQ·QLD → QQQ, SOXL → SOXX, 그 외는 프로필의 기초 ETF)의
  5년 일봉으로 사이클을 다시 만들고, 마지막 봉은 앱의 현재 값(회복 n/6, MA50, 과열·급락·비중)으로 판독합니다.
- 정밀관측소 레버리지 패널의 "L3 회복 DCA 사이클" 표, `leverage_stage`의 `l3_status`·`l3_reasons`.

2단계(이번 PR, 사용자 결정 2026-11-25: 20거래일 간격 + Supabase 저장 승인):

- 저장소: Supabase 테이블 2개(`db_schema.get_leverage_dca_create_sql()`).
  - `leverage_dca_cycles`: 계좌/모드(`account_mode`, 지금은 'total'), ticker, cycle_id(ticker-사이클 시작일), 시작일, L2 자격일,
    사전 총예산, 최대 회차 3, 사용 회차 수, panic_latched, 마지막 실제 회차 실행일, 상태(active/closed), 정책 버전.
  - `leverage_dca_tranches`: cycle_id, tranche_no, 실행 기준일, 계획 금액, 실제 기록 금액(계획 이하), 당시 부족분,
    당시 월적립 배정액, 실행 당시 L3 조건·근거(jsonb), 정책 버전, created_at. 감사 기록이라 insert만 허용하고
    cycle_id + tranche_no 고유키로 같은 회차를 두 번 기록할 수 없습니다.
- `read_current`: 저장된 기록은 같은 cycle_id일 때만 적용합니다(사이클이 끝나 새 사이클이 시작되면 회차·쿨다운 없음).
  사용 회차·누적 투입은 회차 기록에서, 쿨다운은 마지막 기록일을 완료봉 목록에서 찾아 거래일 수로 계산합니다.
- 정밀관측소: 예산 입력·저장, 회차 기록 표, 실행가능일 때만 실제 금액 입력(최대 = 이번 회차 실행가능액) + 확인 체크 + 기록 버튼.
- 이번 달 월적립 배분: 월 적립 계산기가 계산할 때 세션에 남기는 값(`_monthly_plan_alloc`, 이번 달·종목별 최종 배분)을 씁니다.
  계산기를 이번 달에 열지 않았으면 "이번 달 월적립 배분 미확인"으로 후보에 머뭅니다.
- 실행가능 행: 판정 `LEVERAGED_L3_RECOVERY_DCA` "⚡레버리지 L3 회복 DCA: n회차 실행 (사전 예산 1/3)", buyish, 매수액 = 회차 금액,
  게이트 근거 "L3 회복 DCA n/3회차 실행: 사전 예산 1/3 · 최대 …원". 시장방어(레버리지 시장방어)·매크로·데이터 확인은 게이트에서 그대로 막습니다.
  현재가 손절·목표 가격이 없으면 기존처럼 데이터확인입니다.
- 예산이 없는 지금은 1단계와 같은 화면입니다(L3 후보, 실행가능 0).

## 근사와 한계

- 과거 봉의 L2 자격은 현재 평단으로 계산합니다(회차 매수로 평단이 바뀐 이력은 없음).
- 과거 봉의 회복 n/6은 앱 체크의 근사입니다(RS는 SPY 대비 10일 평균 기울기, 기초축 1W는 기초 ETF 하나). 현재 봉은 앱 값 그대로 씁니다.
- 과거 봉에는 시장상태가 없어(None) 과거 봉으로 실행 판단을 하지 않습니다. 현재 봉의 시장방어·매크로·데이터는 실행 게이트가 확인합니다.
- 5년 이력의 첫 봉이 이미 −10% 이하면 "사이클 시작이 가격 이력보다 앞설 수 있음"을 사유에 붙입니다.

## 검증

- 고정 입력 재생(1999~2026, TQQQ·QLD·SOXL, 예산 100, 목표 300): 사이클당 최대 3회차, 패닉 latch 중 실행 0,
  시장방어 봉 실행 0, 누적 투입 ≤ 예산, 회차 금액 ≤ 부족분, L2 자격 없는 실행 0. L3 92건 중 70건은 실행 시점 손실이 −12%보다 작았습니다(과거 L2 자격으로 실행).
- 테스트: `tests/test_leverage_l3_policy.py` 25건.
- parity 재생(41,391 상태, 10거래일 격자): 바뀐 상태는 레버리지 11건뿐입니다. 모두 '회복 전 DCA 보류' → 'L3 후보 (조건부)'입니다.
  게이트는 3건이 방어우선 → 대기, 8건은 방어우선 그대로였고, 실행가능이 된 상태는 0건입니다. 주식·ETF 상태, 엔진 판정, 월간 리밸런싱 배율(엔진 기준)은 바뀌지 않았습니다.
  오늘 큐 체인의 가상 t_mult는 이 11건이 0 → 0.5로 바뀝니다. 앱의 월간 리밸런싱은 이 값을 쓰지 않습니다(HANDOFF의 t_mult 주의 참고).
- 전체 테스트 33 실패 / 10,050 통과, 실패 목록은 main과 같음. `check_refactor.py --scope decision` 1 실패(기존 알려진 실패).
