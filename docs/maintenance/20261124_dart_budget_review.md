# DART 공시 수집 시간 한도 보류 점검(백로그 #5)

작성 2026-11-24 KST. 코드 변경 없음, 점검 기록과 결정 요청.

## 확인한 것

- 순서: `earnings_collection.collect_report_earnings`는 등록된 발행사를 **보유 종목 먼저**, 그다음 오늘점검 입력 순서로 최대 96개 넘긴다.
  한국 발행사는 별도 풀(동시 3개)에서 이 순서대로 처리되므로, 시간 한도에 걸리는 것은 큐 뒤쪽(대개 비보유 관심 종목)이다.
- 예산: 공시 탐색 전체 벽시계 24초(`MAX_SECONDS`), 시작 시점에 정해지고 설정 단계도 같은 예산을 쓴다.
- 한국 발행사 1곳의 콜드 요청: 공시 목록(list.json, 10분 캐시) + 회사 정보(company.json, 하루 캐시) + 재무제표(fnlttSinglAcntAll, CFS 없으면 OFS까지, 10분 캐시).
  즉 캐시가 비면 2~4회 요청이다. 한국 발행사 40여 곳 × 2~3회를 동시 3개·24초 안에 끝내기 어렵다.
- DART 기업 식별 목록은 프로세스 안에 하루 캐시된다. 재부팅 직후 첫 실행만 목록 다운로드(지난 계측 약 10초)를 예산에서 쓴다.
- 10분 캐시 때문에 10분 넘게 간격을 두고 시황을 만들면 매번 콜드 상태가 되고, 같은 큐 뒤쪽 발행사가 반복해서 보류된다.
  (11-24 오전 51건 보류 → 시장별 풀 분리 후 41건. 그 뒤 보류 목록 상당수가 같다.)

## 정책 안에서 바꿀 수 없는 것

예산 24초, 동시 3개, 재시도, 목록 검증, 10분 공시 목록 캐시는 사용자 지시대로 유지한다.

## 결정이 필요한 선택지

1. **재무제표 응답을 접수번호 기준으로 하루 보관**: 재무제표는 공시 접수번호(`rcept_no`)별로 내용이 바뀌지 않는다.
   이미 키에 접수번호가 들어 있으므로 보관 시간만 10분 → 하루로 늘리면, 정상 상태에서 발행사당 요청이 1회(공시 목록)로 준다.
   새 공시가 나오면 접수번호가 달라져 새로 받는다. 단, 캐시 시간 변경이므로 사용자 승인 대상이다.
2. 재부팅 직후 하루 안에 저장된 기업 식별 목록을 바로 쓰기: 첫 실행의 약 10초만 줄어든다. 효과가 작고 최신성 정책이 바뀐다.
3. 지금처럼 유지하고 보류 표시만 계속한다.
