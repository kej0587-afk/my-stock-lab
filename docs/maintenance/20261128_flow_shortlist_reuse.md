# 돈흐름 후보 실행 내 재사용과 선택 함수 분리

## 확인한 중복

자동후보 입력 준비와 최종 화면 맥락 준비가 각각 `build_today_flow_shortlist_df`를 호출했다. 해당 builder의 기존 캐시 분기는 후보프레임과 버전을 읽고 보유/관심 등록상태를 다시 계산한다. 전체 계산 중에는 돈흐름 snapshot이 교체될 수 있으므로 호출 횟수만 보고 무조건 합칠 수 없다.

`FlowShortlistRenderReuse`는 한 번의 `_render_today_queue_tab` 호출에만 존재한다. 같은 snapshot 객체, 같은 캐시프레임 값·순서·dtype·버전, 같은 보유 등록입력·관심목록일 때만 복사본을 공유한다. 보유량/평가액/이름/티커/관심목록 변경, snapshot 교체/제자리 변경, 후보 메타데이터 존재 시 원 builder를 사용한다. 실패 결과를 저장하지 않는다. 다음 화면 실행에는 새 reader를 만든다.

실제 전체계산 refresh 콜백은 기존 builder 경로를 유지하며 새 snapshot을 읽는다. 점수·게이트·금액·시장방어·월적립·L3·캐시 TTL·조회 한도 변경 없음.

## 후속 우선순위

P1은 서버 교체 후에도 소유자별 원계산을 복원할 영구 저장 경로다. 기존 Supabase 개인 저장 구조와 용량을 먼저 점검하고, 아래 UI 분리보다 우선한다. 임의로 CSV를 원판정 입력으로 재구성하거나 새 계산으로 복원 실패를 감추지 않는다.

사전 구조확인: settings는 계좌현금 등 scalar,report_history는 US/KR거래일과 rows제약이 있어 임의blob 저장소로 혼용하지 않는다. 전용snapshot SQL/어댑터가 필요하다. 기존 앱 인증은 검증된owner+서버service client이며 Supabase 사용자JWT가 아니므로 모든 읽기/쓰기의owner필터·응답소유자 검증을 유지해야 한다. 실제 전체payload 크기와 저장실패 재시도 정책은 다음 작업에서 검증한다.

이번 표본의 남은 큰 대기는 DB 캐시미스와 국내 시세 응답이다. 기존 TTL을 늘리거나 조회를 생략해 속도 개선으로 포장하지 않는다. 접힌 브리핑/그래프가 병목이라는 기존 가설은 앞선 실측에서 입증되지 않았다.

다음 큰 UI 함수는 `render_entry_execution_plan`(434줄)이다. 기존 신규진입·보유관리·레버리지 정책은 유지하고, 금액/수량·R/R·분할 표시문구 조립부터 순수함수로 분리할 수 있는지 검토한다. 가격·금액 산정이나 L3 정책 변경과 섞지 않는다. 차트 아래 A/B/C 요약·신규진입 표·단기 관찰까지 운영 검증 범위를 유지한다.

자료부족4건/두거래일 오늘한줄/11월30일 선물13:00ET 기준은 자료·시간이 충족되면 별도 검증한다. 한 항목 완료마다 다음 지시를 요청하지 않고 가능한 후속을 이어간다.
