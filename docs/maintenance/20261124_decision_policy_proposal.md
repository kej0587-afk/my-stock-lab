## 3. 판정코드의 상위 행동군 분류

127개 코드는 이름·라벨·우선순위를 하나도 바꾸지 않고 9개 행동군으로 묶었다. 전체 표는 부록 A에 있다.
사용자가 제안한 8개에서 두 군데를 고쳤다.
- "보유·추매 관리"는 **추매**와 **유지·비중·익절**로 나눴다. 사용자가 할 일이 다르기 때문이다(돈을 넣는가, 넣지 않는가).
- "코어 ETF DCA"에는 일반·신규 ETF 적립을 함께 넣었다. 모두 목표비중 부족분을 채우는 적립형이다.

### 4.2 제안 (판정 코드는 그대로 두고 층의 권한만 정리)

```
 ① 안전관리자: 후보등급·안전상태          → 표시 + RED 신규 차단(현행 유지)
 ② 현장소장: decision_code (127개, 무변경) → 행동군 (9개)
 ③ 기술검토: 패턴·매물대·거래량·구조·위치·기간·유동성·상위시간대
        → CONFIRM / NEUTRAL / CAUTION / BLOCK / DATA_CHECK  (+ 시나리오 상태 8종)
        ※ decision_code를 바꾸지 않고, 판정분류(group)도 올리지 않는다
 ④ 관제탑: 시장 모드(정상/주의/방어/위험/비상) + 매크로 상태      → 게이트 입력

 ⑥ 사이징: 실행가능일 때만 금액. 코어·레버리지·월적립 배율은 decision_code·단계 기반 하나의 표
```

사용자에게 보일 한 줄 (예시. 문구는 결정 후 확정):

> 후보품질 **A** → 현장소장 **상승장 눌림 신규진입**(S급 눌림목) → 기술검토 **CAUTION**(상단 매물대 1ATR 안·돌파 거래량 미확인) · 상태 **정상 눌림** → 관제탑 **주의** → 실행게이트 **대기** → 사이징 —

## 5. 차트 요소의 권장 역할 (기술검토층)

### 5.1 원칙

1. 기술검토는 **현장소장 판정에 대한 의견**이다. decision_code와 판정분류를 바꾸지 않는다. 점수를 더하지 않는다.
2. 결과는 다섯 상태 중 하나다. 우선순위는 `DATA_CHECK > BLOCK > CAUTION > CONFIRM > NEUTRAL`이다.
3. 각 의견에는 근거 ID(pattern, zone, volume, structure, location, duration, liquidity, mtf)를 붙인다. 게이트·최종체크는 이미 있는 `independent_check_summary`처럼 **같은 근거 ID를 한 번만** 센다. 같은 MTF 훼손을 판정, 게이트, 최종체크에서 세 번 세지 않는다.
4. **강제 차단(구조훼손)은 기술검토 의견이 아니라 현장소장의 기존 위험 우선순위로 남긴다.** 해당 코드는 STRUCTURE_DAMAGE_*, PRICE_DRAWDOWN_*, SINGLE_DAY_BREAKDOWN_*, LIVE_GAP_SHOCK_*, DRAWDOWN_20_*, MTF_DAMAGE_NO_ADD이다. 기술검토는 이 코드들을 "이미 차단됨"으로 참조만 하고 다시 BLOCK으로 세지 않는다.
5. 기술검토의 BLOCK은 "구조적으로 지금 실행 부적절"이다. 게이트에서 대기로 갈지 방어우선으로 갈지는 사용자가 정한다(D10). CONFIRM이 실행을 새로 허용하거나 사이징을 늘릴 수 있는지도 D10에서 정한다. 권장안은 **CONFIRM은 표시만 하고 권한은 없음**이다. 상승장 대응은 ②에 이미 있으므로, ③은 확인과 경고에 집중한다.

### 6.1 정식 전략으로 편입하는 방법

- 위 기능을 "예외"가 아니라 행동군 2(상승장·대장주)와 3(회복)의 **정식 진입 유형**으로 문서화한다. 이름은 그대로 두고, 판정 매뉴얼의 "예외" 표현만 정리한다.
- 각 유형에 "어떤 보수 규칙을 대신하는지"를 한 줄로 붙인다. 예: 불뿜는 대장주 → %B 0.95 하드차단의 대장주 예외.
- 게이트에서 막히는 이유를 유형별로 따로 보여 준다. R/R 근접 고점, 투영상단, MA5 대기 코드가 그 예다.

### 6.2 지금 남아 있는 상승장 병목: R/R 목표 정의 (코드 사실)

- 손절은 2ATR이다. 목표는 가까운 피벗 고점 → 먼 피벗 고점 → 없으면 +4ATR 투영이다(`build_rr_context`, decision_engine.py:556).
- 고점 아래 0.5ATR에 있는 종목은 R/R이 0.25다. 신고가 위에서는 R/R이 항상 2.0이지만 "투영상단"이라 대기다.
- 결과적으로 행동군 2의 대부분이 게이트에서 대기가 된다. 이것은 판정 코드나 임계값이 아니라 **R/R 목표의 정의** 문제다.

### 8.5 이 우선순위는 의도된 것인가

- **차단 우선은 의도된 것이다.** 08-21 사유 문구, 09-22 주석 "Explicit per-row STORM still wins", 10-31 문서 "레버리지 특례도 이 조건을 우회하지 못한다"가 근거다.
- **"실행가능 경로가 아예 없음"의 의도는 확인되지 않는다.** 09-23 회복정찰의 목적이 "묻히지 않게"(보이게)였으므로, 사용자가 직접 확인하고 실행하는 구조를 의도했을 수는 있다. 하지만 이를 명시한 문서는 찾지 못했다 → D8.

### 8.6 하나의 레버리지 전용 정책표로 통합하는 방법 (값은 결정 전까지 현행 유지)

1. 상품별 정책 모듈 하나(`leveraged_policy` 같은 이름)가 **단계** 하나를 낸다.
   - 단계 후보: 미보유 관찰 / 목표0·충족 제외 / 일급락 차단 / 과열패스 / 회복 전 보류 / 약·중·강 하락 후보 / 패닉권 관찰 / 초기 회복 정찰 / 수익권 관리
2. 엔진 코드, Today 재판정, 월적립 배율, 게이트, 레버리지 패널이 모두 이 단계를 읽는다. 라벨 글자는 읽지 않는다.
3. 통합 표의 열은 다음과 같다.
   - 하락 기준: 평단 대비와 고점대비 중 무엇을 쓸지
   - 과열 기준
   - 회복 조건
   - 시장 모드별 허용
   - 배율
   - 게이트 결과
4. 첫 이행은 **현재 결과를 그대로 재현하는 표**다. 동등성 테스트로 확인한다. 그러려면 지금 화면마다 다른 결과 중 무엇을 정답으로 삼을지 먼저 정해야 한다(D8). 기본 권장은 Today·정밀(단계표) 결과다.
